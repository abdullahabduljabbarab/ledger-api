Guarantees

What makes it correct

Double entry

Every committed transaction produces balanced entries. Balances are derived from the journal rather than stored as mutable values, so a balance cannot drift from its history.

SUM(entries) = 0

Concurrency control

Row locks taken in deterministic order prevent deadlocks between competing transfers, and a transaction-scoped advisory lock serialises appends to the audit chain.

SELECT ... FOR UPDATE

Idempotency

Retries are safe. A repeated key returns the original transaction, while the same key sent with different parameters is rejected outright rather than silently accepted.

SHA-256 request identity

Independent audit

Ledger state is recomputed through a verification path that shares no code with the write path, so it re-derives the truth instead of re-reading what the service already believes.

Engineering

Testing that changed the architecture

Load testing exposed a fork in the tamper-evident chain that the original 52-test suite had never reached. The ledger invariants held throughout, the audit layer caught it, and the fix and its regression test brought the suite to 58.

Before
Writer A ──┐
           ├── reads tip #41
Writer B ──┘
             ↓
        CHAIN FORK

Two concurrent transfers read the same chain tip and both linked to it. Ordering by created_at made it worse, because that column holds transaction start time rather than commit time.

After
#41 → #42 → #43
  serialized append
             ↓
         VERIFIED

Appends serialise on a transaction-scoped advisory lock, and true order is recorded in a unique chain_seq column, so a fork is rejected by the database rather than accepted.

PostgreSQL advisory lock chain_seq uniqueness regression tested migration re-anchored 417 rows
